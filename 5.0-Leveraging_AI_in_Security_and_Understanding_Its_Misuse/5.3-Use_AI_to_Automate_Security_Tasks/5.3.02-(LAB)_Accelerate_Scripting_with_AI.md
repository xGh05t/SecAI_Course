## Scenario
In security work, automation often starts small - a quick Python script to parse output, filter alerts, or check system configurations. But those scripts rarely run perfectly the first time. Using AI as a coding assistant can accelerate your workflow, helping you debug issues, improve reliability, and extend functionality safely.

In this lab, you'll explore how to use an AI assistant to fix, test, and iterate on Python scripts in a structured way. You'll see how AI can help you troubleshoot syntax errors, refine logic, and harden your code through better validation and documentation - all while maintaining control over what the script actually does.

> [!IMPORTANT]
> **The Mission**:
> - Use AI to diagnose and correct common scripting issues.
> - Iteratively test and refine your script in VS Code until it runs gracefully.
> - Extend the working script by adding new capabilities.
> - Use AI assistance to plan for large-scale code refactors.

The goal isn't to rewrite the code, but to make its intent visible at a glance.

### Architectural analysis
Before you can change code in a meaningful way, you need to understand the structure it already has-and the assumptions buried inside it. Architectural analysis gives you the ability to zoom out from individual lines of code and see the shape of the system: how data flows through it, what the script expects to be true, and where those expectations might break as requirements evolve. This step isn't about writing code, or even fixing anything yet. It's about building a clear mental model so that the solution you eventually choose is grounded in how the script actually works, not how you hope it works.

```
The attached Python script parses security threat data from JSON files. Currently it only handles a single JSON object, but I need to extend it to handle both:
- Single object format: { "Event": {...} }
- Array format: [ { "Event": {...} }, { "Event": {...} } ]

Please analyze and provide a structured analysis:
1. What architectural assumptions does this code make?
2. Why will it fail with an array input?
3. At a high level, what needs to change to support both formats?
4. What backward compatibility concerns exist?

```

### Solution approaches
Now that you understand why the script breaks, the next step is to explore different ways it could be improved. Instead of zeroing in on the first idea that comes to mind, this stage is about widening the field - mapping out multiple viable approaches, the tradeoffs behind each, and how they'd affect the script's structure going forward. The goal isn't to write code yet, but to see the landscape of options clearly enough to make an informed choice.

```
Based on your analysis, let's explore solution approaches. Please brainstorm 3-4 different approaches for making this code handle both single objects and arrays of events.
For each approach, provide:

Name: [Descriptive name for the approach]
How It Works: [2-3 sentence explanation]

Pros:
[Advantage 1]
[Advantage 2]

Cons:
[Tradeoff 1]
[Tradeoff 2]

Complexity: [Low/Medium/High]

Backward Compatible: [Yes/No]

Focus on different architectural strategies, not complete code implementations.

Example approaches might include: type detection, wrapper functions, etc. But don't limit yourself to these.
```

### Implementation planning
Once you've chosen an approach, the next step is turning that idea into a realistic path forward. This phase is about sequencing the work - breaking the change into small, testable steps that keep the script in a working state as you go. Instead of thinking in terms of final code, you're designing the roadmap: what to change first, what to verify, and how each phase builds on the last.

```
I've decided to go with the wrapper functions approach. Please help me break the implementation into small, testable phases.

For each phase, provide:

Phase [N]: [Phase Name]
Goal: [What this phase accomplishes]
Changes Needed: [Specific change 1], [Specific change 2]
Files Modified: [Which files/sections]
Testing: [How to verify this phase works]
Estimated Time: [Minutes/hours for a junior developer]

Guidelines:
Keep phases small (each should be completable in under 30 minutes)
Each phase should leave code in a working state
Later phases should build on earlier ones
Include a phase for testing backward compatibility
Aim for 3-5 phases total
```

At this point, you've built something more valuable than a quick fix: a clear, phased plan for how to evolve the script without breaking its existing behavior. In a real project, this is where planning hands off to implementation. Each phase you outlined could now become its own prompt - small, focused, and easy for the model to translate into real code. While we won't implement the changes here, you now have the blueprint for how to move from high-level design to concrete changes, one deliberate step at a time.
