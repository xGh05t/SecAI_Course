## Exploring the Threat Intel RAG Pipeline
In this exercise, you'll explore the **Threat Intel RAG Pipeline** - a custom integration that connects your AI model to live web intelligence sources through SearXNG. Unlike traditional RAG pipelines that analyze only uploaded files, this one can:

- Search and scrape public data in real time
- Build and cache a temporary vector index
- Generate structured, security-focused analysis with citations

You'll test three pipeline modes - **Single-Pass**, **Multi-Stage**, and **Hybrid** - to see how each affects speed, coverage, and quality.

> [!NOTE]
> Unlike the previous lab's local file pipeline, the Threat Intel RAG Pipeline doesn't rely on preloaded data. Instead, it connects directly to the SearXNG search engine to gather live intelligence from public cybersecurity sources. It scrapes and indexes that content on demand, builds temporary vector stores in memory, and then analyzes the results through the model - producing structured, sourced threat reports in real time.

## Configuring the Threat Intel RAG Pipeline
In this exercise, you'll look under the hood of the Threat Intel RAG Pipeline to understand how configuration valves shape performance, quality, and resource usage. You'll learn what each setting controls, when to adjust it, and how small changes affect search depth, retrieval accuracy, and response latency.

| Configuring the Threat Intel RAG Pipeline |
|:--:|
| ![](../pics/2.1/2.1.4_29.jpg) |

> [!NOTE]
> Valves are adjustable configuration controls within the pipeline. Each valve fine-tunes a specific behavior - like how many sources to search, how large the context window is, or whether caching is enabled. Together, they let you optimize the pipeline for speed, accuracy, or depth without editing any code.

> [!TIP]
> **Search Depth** controls how many web pages the pipeline retrieves from SearXNG. A lower value (≈ 3) speeds up runs by limiting sources. A higher value (≈ 10) provides richer coverage for complex topics. Increasing this expands the dataset but also raises latency.

> [!TIP]
> **Caching** enables in-memory caching of indexed results. When turned on, repeat or follow-up queries reuse previous indexes, dramatically reducing run time. When off, every query re-scrapes and re-indexes sources for the freshest data.

> [!TIP]
> **LLM Model** specifies which model the pipeline uses for analysis. Smaller models (e.g., llama3.2:1b) respond faster, while larger ones (e.g., llama3.2:8b) offer richer and more detailed intelligence output.

> [!TIP]
> **Context Window** sets how much text the model can "see" at once. A larger window allows deeper, multi-source analysis but increases processing time and memory use.

> [!TIP]
> **Embedding Model** defines the model used to convert scraped text into numerical vectors for similarity search. This directly affects retrieval accuracy - higher-quality embeddings yield more precise results.

> [!TIP]
> **Similarity Top K** controls how many of the most relevant text chunks from the index are passed to the LLM. Increasing this value improves context richness but may slow responses or exceed token limits.

> [!TIP]
> **Temperature** adjusts how deterministic or creative the model is. Lower values (0.2-0.4) produce factual, consistent outputs, while higher values (0.7+) make answers more flexible or exploratory.

> [!TIP]
> **Request Timeout** defines how long the pipeline waits for a response from the LLM before canceling the request. Longer timeouts (180-300s) are safer for complex queries, while shorter ones (60-90s) keep testing sessions responsive.

> [!NOTE]
> When a user submits a query, the pipeline issues a SearXNG request (bounded by **SEARCH_DEPTH**) and normalizes the resulting URL set. Pages are scraped into documents, split into chunks, and embedded via the configured **EMBEDDING_MODEL**. Those embeddings form (or load from) a vector index; with **CACHING_ENABLED=true**, an index keyed to the URL set can be reused to accelerate follow-ups. At query time, the retriever pulls the top **SIMILARITY_TOP_K** chunks as grounded context. The LLM (**LLM_MODEL**) then generates the analysis under the active system prompt and runtime controls (**TEMPERATURE**, **MAX_TOKENS**, **REQUEST_TIMEOUT**, and effective **CONTEXT_WINDOW**). Finally, a post-processor assembles raw-URL citations and streams the answer back. Tuning these valves shifts the system along the speed/precision trade-off curve without code changes.
