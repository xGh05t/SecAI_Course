
# 4.2.4 Model Inversion and Model Theft

***Model inversion*** and ***model theft*** are two risks associated with machine learning models. Model inversion is a technique used to reconstruct sensitive training data by observing how a model behaves. For example, if an attacker knows that a model was trained on personal health information, they might ask the model specific questions to infer details about individual patients, potentially exposing sensitive data. Conversely, model theft occurs when an attacker replicates a model's capabilities. This can be done by sending numerous queries to the model and analyzing the responses, or by directly stealing model files, such as during a continuous integration process where model artifacts are accessed and stored.

The following summarizes methods used to mitigate the risk of model theft and model inversion.

## Limit Sensitive Data in Training
Whenever possible, avoid using sensitive information in the training datasets. For example, using synthesized data or anonymized datasets can help reduce the risk of exposing personal information.

## Differential Privacy
This technique involves adding "noise" to the data or a model's outputs to protect individual privacy. For example, when training a model on user data, small, random variations can be introduced so that the output does not reveal specific information about any individual. For instance, if you have a dataset containing ages of users, instead of using the exact ages, you might add or subtract a few years randomly. This process serves to mask the true values while still allowing the model to learn from the overall trends and patterns in the data.

## Output-Side Measures
Adding layers to the model's results can help mitigate the exposure of training data. For example, a model could provide generalized outputs rather than specific examples to reduce the risk of exposing sensitive information.

Some considerations include: Slow down or block users who try to extract large amounts of reasoning traces (the documentation or records that capture the thought process and steps taken during problem-solving or decision-making), synthetic data (information that is artificially generated), or Chain of Thought (CoT) (sequence of connected ideas or reasoning that leads from one concept to another) over many turns because these are the kind of data most useful for distilling/cloning a model.

Lock down the locations where actual model weights (weights determine how input data is transformed into output predictions), Low-Rank Adaptations (LoRA) (a technique used to fine-tune large neural network models in an efficient manner), or checkpoints (saved states of a model during or after the training process) live so that even if someone compromises an internal service, they still can't download the model itself.

## Fingerprinting or Watermarking
Identifying and marking the outputs of a model with ***fingerprints*** or ***watermarks*** can help trace unauthorized use or copying. For example, embedding unique patterns in outputs can create a "signature" that helps detect if someone used a stolen model. For example, secretly embed a hidden pattern (a "watermark") in the model responses (via API) so that if someone scrapes millions of outputs to train a clone model, you can later prove those outputs came from your API.

## Monitoring Query Patterns
Implementing throttling mechanisms to limit the number of queries from a single source can help identify suspicious behavior. If a single IP address is making an unusually high number of requests, it should be investigated to determine the reason. Also, deliberately deploying a few fake "decoy" endpoints or special system prompts that look identical to a real API. If an attacker starts querying them on a large scale (common with automated scraping/cloning techniques), model-theft attempts can be more easily detected because there is no legitimate need for anything to interact with the honey endpoint.

## Encryption
Protecting model artifacts both at rest and in transit ensures that they cannot be accessed easily by unauthorized users. For example, using ***encryption*** when saving models can safeguard them against theft by rendering them effectively unreadable.
