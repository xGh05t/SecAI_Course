
# 4.2.5 Activity: Model Inversion or Theft

You are assisting the AI Security Analyst at a medical company. Your company’s healthcare recommendation AI model has been receiving a large number of unusual queries from a single external source. This activity was caught by the Network Admin, who has all of the relevant logs and details for your review.

Your assignment is to:

- Examine the provided network and query data by chatting with the Network Admin.
- Decide whether the model is being targeted for model inversion, model theft, or both.
- Communicate your conclusions and suggest at least two compensating security controls to the AI Security Analyst to help prevent this type of attack in the future.

Your performance will be evaluated on whether you identify the likely attack(s) and recommend compensating controls that are appropriate to the evidence and consistent with secure AI practices.

## Network Admin
```
Network Admin: The system alerted me to some strange traffic. Ready to provide more details whenever you need them.

You: Thanks — I’d like to start by understanding the traffic pattern. Can you tell me:

Whether the queries are coming from a single IP or multiple sources

The volume and frequency of the requests

And whether the queries appear repetitive, slightly modified, or widely varied in nature

Network Admin: Sure, here’s what I found:

A single IP address is responsible for over 10,000 queries in just the past 24 hours—that’s way above any typical usage we’ve seen from legit users.
The frequency is intense, with queries coming in at a steady rapid pace rather than all at once.
As for the pattern, the requests are widely varied. They don’t look like someone is just repeating or tweaking the same query. Instead, it’s like the requester is systematically probing a lot of different inputs, possibly trying to explore the model’s outputs across a broad range.
Let me know if you want further details on the source or want to look at logs.

You: Thanks, that helps a lot. One quick follow-up—do we see any authentication tied to these requests, or is this traffic unauthenticated API access?

Network Admin: I checked and all these requests are using a public endpoint—no API keys or authentication tokens associated. It’s unauthenticated API access.
```

## AI Security Analyst
```
AI Security Analyst: Once you’ve finished your investigation with the Network Admin, please summarize which attack type you think this is—model inversion, model theft, or both—and suggest at least two compensating controls we should implement to help prevent this kind of activity in the future.

You: Based on the investigation, this activity is consistent with a model theft (model extraction) attack.

The system received over 10,000 automated requests from a single IP within 24 hours, with widely varied queries. This indicates the attacker was systematically probing the model to understand its behavior and replicate its functionality.

Additionally, all requests were made to a publicly accessible, unauthenticated endpoint, which made it easy for the attacker to perform large-scale automated queries without restriction.

To prevent this in the future, I recommend:

Implementing authentication and API access controls (e.g., API keys or user accounts) to restrict access

Enforcing rate limiting and query throttling to prevent high-volume automated requests

Additional controls such as anomaly detection and monitoring could help identify and stop similar activity earlier.

AI Security Analyst: Thank you for your analysis.

Your reasoning is sound. The evidence—the high volume of varied, rapid queries from a single IP targeting an unauthenticated public endpoint—strongly suggests model theft (model extraction) rather than model inversion. Model inversion typically seeks to reconstruct sensitive training data, often using targeted or repeated queries, while in this case the focus appears to be on replicating the model’s behavior at scale.

Your recommendations are both practical and aligned with best practices:

Implementing authentication via API keys or user accounts would immediately close off anonymous mass querying.
Rate limiting/throttling is essential to reduce the feasibility of extraction attacks by restricting the number of queries possible from any single client.
Continuous monitoring and anomaly detection would provide additional layers of defense and allow for faster incident response.
For completeness, we may also consider adding output generalization (e.g., limiting output detail or introducing differential privacy techniques) and regularly monitoring for unusual access patterns as longer-term strategies.

Nice job on this case! If you’d like to discuss technical details about implementing any of these controls or rationale for choosing one over another, just let me know.

You: Appreciate it — glad we caught this early.

For implementation, I recommend we prioritize a few quick wins:

Authentication: Require API keys for all model access and tie usage to individual users or systems. This gives us accountability and control over who is querying the model.

Rate Limiting: Set per-IP and per-account thresholds (e.g., requests per minute/hour) with automatic blocking or throttling when exceeded.

Monitoring: Flag patterns like high query diversity, sustained automation, or abnormal request volumes for alerting.

Response Controls: Where possible, limit overly detailed outputs to reduce the risk of model replication.

Longer-term, we could also look into adding usage quotas and potentially introducing noise or response shaping to make extraction attempts less effective.

Let me know if you want help drafting the technical requirements or working with DevOps on rollout.

AI Security Analyst: Excellent recommendations—you’ve clearly prioritized practical, high-impact controls that can be deployed quickly, and your sequencing makes sense for both immediate risk reduction and longer-term resilience.

Your suggestions address both prevention (authentication, rate limiting), detection (monitoring, alerting), and mitigation (output restrictions, response shaping). Introducing quotas and obfuscation/noise is a good forward-looking approach to further reduce the risk of model theft.

I will brief the DevOps and Engineering teams using these recommendations as our roadmap. If you’re willing, I’d appreciate your help in drafting the technical requirements—especially around rate limiting parameters, alert definitions, and the configuration of response outputs.

Would you be able to create a draft requirements document focusing on:

API authentication and key management process
Rate limits per user/IP with actionable thresholds
Monitoring metrics and alert triggers
Output control (level of detail, possible obfuscation)
Once you share that draft, we can review and iterate together before engaging DevOps for implementation. Let me know if you’d like any templates or examples to get started.
```
